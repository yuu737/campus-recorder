## 1. 4 棟を同時に回す（本番と同じ形）
- **4 棟を 4 本の列として同時に回します。** 1 本の列の中では工程を順に進めます（本番の `run_pipeline` が棟ごとに工程を順に回すのと同じ）。列どうしは待ち合わせません。
- 共有の台帳（写真の索引・登録台帳・決定・CC0 の台帳・site.json）の書き込みと GPU（Blender・headless の Edge）は、**道具が鍵で 1 つずつにします**（`recorder/ledger.py`、11/7 に入れた。審査のコードレビュー A7 の直し）。あなたが「この係とこの係を同時に走らせない」と組み合わせを考える必要はありません。係が道具のコマンドで書けば、道具が待たせます。本番でも同じ仕組みで守るので、ここで試すのが目的の 1 つです。
- 列ごとの工程は、`.venv/Scripts/python -I -X utf8 -m recorder agent tasks <棟id>` が出す `out/<棟id>/agent_tasks.md` の 11 工程の順（本番の `run_pipeline` と 1 文字も違わない依頼文）：
  1 `satsuei` → 2 `shiwake` → 3 `kansatsu` → 4 `kazoe` → 5 `sokuryo` → 6 `sekkei` → 7 `seizu`（**コマンド** `recorder run data/buildings/<棟id>.json --fast`）→ 8 `mejirushi` → 9 `kenshu` → 10 `seizu_final`（**コマンド** `recorder run data/buildings/<棟id>.json`）→ 11 `web`（**コマンド** `recorder site export-web --with-coverage`。全体の書き出しなので 4 列が 10 まで終わった後に 1 回だけ）
- 回し方：4 本の列の 1（撮影係）を同時に呼び、ある列の工程が終わったら、その列の次の工程を呼ぶ。係の工程は `subagent_type=<係>`（見出しの括弧の係）で、依頼文をそのまま渡す（先頭に「読まない物」の一文）。モデルは係の定義のまま（Haiku・Opus）。コマンドの工程（7・10・11）は係を呼ばずに Bash で打つ。鍵で待つことがあるので背景で走らせてよい。
- 同時に動かす係は最大 4（1 列に 1 本）。使用量や速度の上限で失敗が続く時は、同時の数を 2 に下げてよい（進行役の決定として記録）。
- **`--zero` の後の棟は「全部渡す」**（11/7 の利用者の判断。本番では職員が棟ごとに入れる所なので）：本部棟 76・図書館 79・タワー75 131・共通講義棟南 29・敷地 6、空は 19 枚。出どころは 3 つ：職員の振り分け（`building_source: staff`。タワー75 102・共通講義棟南 29）、11/3 の取り込みの時に付いた棟（`intake_proxy`。本部棟 61・図書館 27・タワー75 29・敷地 6）、職員が「図書館か本部棟」と候補だけ示した写真で前の仕分け係が選んだ棟（`prior_sort`。本部棟 15・図書館 52）。**面は全部空**（仕分け係が決める）。空の 19 枚（候補だけで決まっていない 2・誰も決めていない 17）は、仕分け係が棟から決める。`photos set-face` は棟がある写真の棟を変えないので、仕分け係が別の棟だと見た時は `skipped` に理由が出る → その件数と理由を `記録.md` に書く（取り込みの時の棟の誤りの候補）。
- 結果のまとめと README には、棟の出どころを 3 つに分けて書く（職員の振り分け／11/3 の取り込みの時に判断役が付けた棟／職員の候補から前の仕分け係が選んだ棟）。後の 2 つを「職員が振り分けた」と書かない。
- 棟が決まっていない写真は、どの列の仕分け係も取りに来る。`recorder photos set-face` は棟が空の写真にだけ棟を書くので、先に決めた列が取り、後の列には `skipped` に理由が出る。取り合いの件数を記録する。
- 係が共有の台帳を道具を通さずに自分のスクリプトで書いた形跡（報告や出力にその旨がある、索引・登録台帳の件数が急に減った等）があれば、詰まり（kind: gate）に記録し、その工程をやり直させる。
- 1 工程ごとに（**時間とトークンの記録。README と動画の費用・時間の表はここから作る**）：
  - 工程を始める直前に、時刻を控える（`date +%Y-%m-%dT%H:%M:%S`）。
  - 終わったら `.venv/Scripts/python -I -X utf8 -m recorder agent log <棟id> --step <工程名> --model <haiku|opus|code> --started-at <始めの時刻> --ended-at <終わりの時刻> --seconds <秒> --tokens <トークン> --tool-uses <回数> --attempt <何回目> --result <ok|retry|skipped|failed> --note "<1 行>"`
    - 工程名は `agent_tasks.md` の見出し（`satsuei`…`seizu`・`seizu_final`・`web`）。その列の最初の工程だけ `--new`。
    - 係の工程の秒・トークン・道具の回数は、係が終わった時の結果の使用量（`duration_ms`÷1000・`subagent_tokens`・`tool_uses`）をそのまま写す。コマンドの工程は `--model code`、秒は始めと終わりの差、トークンは書かない。
    - やり直した時も 1 回ごとに記録する（`--attempt 2`）。失敗した回も消さない。
    - 道具が、その間にこの棟のコマンドが鍵を待った秒（`lock_wait_s`）を `out/.locks/waits.jsonl` から自動で足し、記録 `out/<棟id>/pipeline_<日時>.json` と `data/reports/<棟id>/pipeline_<日時>.json` に、工程ごとの秒・トークン・待ちと、棟の合計（`seconds_total`・`tokens_total`・`wall_seconds`・`lock_wait_total_s`）を書く。
    - 費用は、Claude Code の使用量ではトークンの合計しか分からないので書かない（本番の API で SDK が出す）。
  - `recorder agent events <棟id>`
  - 棟 JSON があれば `recorder validate --strict data/buildings/<棟id>.json`。警告が出たら、その係に 1 回差し戻す（値は係が直す。あなたは直さない）
- **メジャーの写真は、あってもなくても最後まで通す。** 仕分け係がメジャーの写った写真に印（`ruler: tape_measure`）を付け、測量係が `recorder photos list --building <棟id> --ruler tape_measure` で探す。あればその棟は縮尺が measured の道、無ければ PLATEAU 以下の estimated の道（撮影依頼が 1 件足される）。どちらも完遂。今の索引には 11/7 の朝の時点でメジャーの写真は無い見込み（本番で使う予定）なので、疑似本番は主に「無い時の道」を試す。印が付いた写真があれば、どの棟のどの写真かを `記録.md` に書く。
- 共通講義棟南は前の結果が無く、写真は 11/5 の 29 枚だけ。棟 JSON は測量係の最後の `recorder new kyotsu-minami --from-site` で作る。写真が少ないので、撮影依頼が多く出てよい。研究室・掲示物が写っている写真が無いかを、撮影係と仕分け係に見させる（決まり 4）。

## 2. 進行役の権限（11/7 に利用者が決めた線引き。本番の進行役も同じ）
**流れは強く決める。道具と規則は変えない。止まらずに最後まで通す。**

決める根拠は、`recorder agent events` の出力と、そこに名前の出たファイル（`soten.json`・`requests`・再検収の要約など）、validate の出力だけにします。係とのやり取りで見えた事を根拠にしない（本番の進行役は事件の一覧と争点しか見ないので、それと同じ条件にする）。

してよい事（流れの決定）：
- **やり直す**：同じ工程を同じ係の定義で、1 工程につき 2 回まで。
- **格上げ**：Haiku・Sonnet の係が失敗したら、同じ係の定義のまま Opus で呼び直す（Agent の model を opus に）。
- **飛ばす**：その棟のその工程を飛ばして次へ進む。何が欠けたか（どの値が unknown のままか、どの写真が使われなかったか）を記録する。
- **行き詰まり（stuck）の決定**：`shinko.md` の選択肢から決める。どちらの主張を採るか／仮説の 3 規則（symmetry・same_block・footprint）の範囲で仮の形にするか／unknown にして撮影依頼を出すか。決めた事を係に渡して、その係にやり直させる。
- **語彙（vocab）**：既存の語彙の composite で近似するか、unknown と `requests`（kind: tool）で残す。新しい語彙のコードは足さない（本番用の直しに書く）。
- **アセット（asset）**：CC0 だけ。`recorder agent decide` で決定を残し、`recorder assets fetch`。見つからなければ箱のまま。
- **人を呼ぶ（human）・完成判定（done）**：記録して進む。撮影依頼の返事は待たない。
- **根拠の門（11/7）**：validate が「measured の根拠の写真が仕分けと合わない／low で未確認」と警告したら、その写真を根拠にした値を書いた係（設計係・検収係）に差し戻し、**estimated に直させる**か、仕分け係に `faces` を足させる（写真が本当にその面も写しているなら）。職員の確認は疑似本番では来ないので、確認待ちの写真は estimated のまま進める。`recorder photos to-confirm data/buildings/<棟id>.json` の件数（職員が確かめれば measured に戻せる写真の数）を棟ごとに結果のまとめに出す。あなたが代わりに `photos confirm` を打たない（職員の仕事）。
- **同時の数と順番を変える**：同時に動かす列の数（4 → 2 など）や、列の中の工程の順を変えてよい（ぶつかりは道具の鍵が防ぐ）。
- **同じ事件が同じ棟の同じ工程で 2 回目に出たら**、その工程はそこで止めて記録し、**ほかの工程とほかの棟は続ける**。

してはいけない事（どんなに詰まっても）：
- 棟 JSON の値や `scripts/design_<棟id>.py` を自分で書く・直す（書くのは設計係と検収係だけ）。係の仕事を自分でやる。
- 道具のコード（`recorder/`・`scripts/`・`tests/`・`web/`）を直す。門のしきい値・validate・検収の合否を緩める。
- `CLAUDE.md`・`.claude/agents/`・`data/rulers.json`・`data/vocab.json`・`docs/手順_エージェント.md` を書き換える（規則の案は「詰まり」の記録に書く。適用は通しの後）。`data/decisions.json` は `recorder agent decide` 以外で書かない。
- 期間前の写真、`trial/` の中身、Google 由来の物を使う。根拠の無い値を書く・根拠を作る。
- 道具が落ちて回避策が無い時は、**その棟のその工程を飛ばし**、エラーの全文を「詰まり」に記録して先へ進む（直すのは通しの後の開発の仕事）。

**unknown と撮影依頼で終わるのも完遂です。** ただし報告では「形がある割合」と「根拠がある割合」を必ず分けて出す（手順書の割合の節）。

## 3. 止まってよい時
- 使用量の上限などで、もう 1 本も係を呼べない時だけ。その時は `data/reports/疑似本番_11-07/引き継ぎ.md` に「どの棟のどの工程まで済んだか・次にやる事・開いている詰まり」を書き、そこまでをコミットして止まる。
- 係が落ちた時（エラー・回数や予算の上限）は止まらない：1 回やり直す → 格上げ → 飛ばして記録、の順。

## 4. 記録（`data/reports/疑似本番_11-07/`）
- `記録.md`：時系列。1 行に「時刻・棟・工程・係・モデル・秒・トークン・結果 1 行」。4 本の列が混ざるので、棟 id を必ず先頭に。
- 時間・トークン・鍵の待ちは、上の `recorder agent log` が棟ごとの `data/reports/<棟id>/pipeline_<日時>.json` に残す（別のファイルは作らない）。全体の経過時間（最初の係を呼んだ時刻〜最後の報告）だけ `記録.md` の最初と最後に書く。鍵の待ちの元の記録は `out/.locks/waits.jsonl`（git 管理外）なので、終わりに `data/reports/疑似本番_11-07/waits.jsonl` へ写す。
- `詰まり.json`：詰まり 1 件ごとに
  `{"id": "J-001", "at": 時刻, "building": 棟id, "step": 工程, "agent": 係, "kind": "stuck|vocab|asset|tool_error|agent_error|gate|data|other", "symptom": "何が起きたか", "evidence": ["コマンドと出力の要点・ファイルのパス"], "action": "retry|escalate|skip|decide|composite|unknown_request|other", "effect": "その回避で結果がどう変わったか（unknown に落ちた値・使われなかった写真など）", "fix_for_honban": {"target": "tool|procedure|prompt|agent_def|pipeline", "where": "ファイルや関数", "proposal": "本番での直し方"}, "status": "open|worked_around|stopped"}`
- `決定.json`：進行役の決定 1 件ごとに
  `{"id": "K-001", "at": 時刻, "building": 棟id, "event": {"kind": 事件の種類, "why": 事件の理由, "evidence": events の evidence}, "decision": "決めた事", "reason": "理由（根拠は events とそのファイルだけ）", "result": "その後どうなったか（やり直した工程・unknown の数など）", "rule": "次から係で済むようにする規則の 1 行（手順書へは通しの後に）", "record": "pipeline_<日時>.json の名前"}`
  （`data/decisions.json` は語彙とアセットしか受け付けないので、行き詰まり・飛ばし・やり直しの決定はここに書く。本番では台帳を広げる予定）
- `監査.json`：`start`（HEAD・時刻）、`end`（HEAD・時刻）、`git diff --stat <start の HEAD>` と作業ツリーの差分、`touched_rules`（`recorder/`・`scripts/`・`tests/`・`web/`・`CLAUDE.md`・`.claude/agents/`・`data/rulers.json`・`data/vocab.json`・`docs/手順_エージェント.md` に差分があれば true とファイル名。`data/decisions.json` は `recorder agent decide` 以外の差分があれば true）。true ならその通しは「規則に触れた」として結果のまとめの最初に書く。

## 5. 終わり
1. 4 棟が終わったら：`recorder site export-web --with-coverage`、棟ごとに `recorder report data/buildings/<棟id>.json`（`--shots` は headless の Edge がこの環境で起動してすぐ終わることがある。落ちたら絵なしで出し、詰まりに記録。Edge が残っていたら必ず終了させる）、`recorder counts data/buildings/*.json`、4 棟の `recorder validate --strict`。
2. 終わりの監査を `監査.json` に書く。あわせて記録の抜けを確かめる：4 棟それぞれの `data/reports/<棟id>/pipeline_<日時>.json`（runner subagent）に、1〜10 の工程が全部あるか（やり直しは 2 行以上でよい）、秒とトークン（コマンドの工程は秒だけ）が空でないか。抜けがあれば `記録.md` の時刻から埋め、埋められない物は詰まり（kind: other）に書く。
3. **結果のまとめ** `data/reports/疑似本番_11-07/結果.md`：
   - 最初に：進行役は Opus 5.5（Fable の代役）、規則に触れたかどうか、開いている詰まりの数
   - 棟ごと：使った写真・面に振り分けた写真・登録できた写真、measured・estimated・unknown の数、形がある割合・根拠がある割合、撮影依頼の数（職員宛て・道具宛て）、事件と決定の数、係ごとの秒・トークン・費用
   - 時間：全体の経過時間（最初の係を呼んでから最後の報告まで）、棟ごとの経過時間、係の秒の合計（4 列を足した物。経過時間との比が並列の効き目）、鍵を待った秒（台帳・GPU 別、どのコマンドで待ったか）、トークンの合計（棟ごと・係ごと）
   - 並列の確かめ：取り合いになった写真の数、`skipped` の理由、鍵の待ちが長かった所（本番で同時の数を決める材料）
   - 本番用の直しの一覧（詰まり.json から、効く順に。どのファイルの何を直すか）
   - `trial/zero/<日時>/` の前の版と、件数だけの比べ（measured・estimated・unknown・登録の数）
   - 縮尺の道：棟ごとに「メジャーあり（measured の道）／なし（estimated の道）」、使った物差し、2 本目の物差しとの差（%）。measured の数が前の版から増えた棟は、縮尺の付け替えで値が何 % 動いたかも書く（11/6 の模擬採点で「書かないと数字を盛ったと読まれる」と言われた条件）
