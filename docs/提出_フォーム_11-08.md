## 7. 開発中に一番詰まった場面（必須）

公式の設問の順（何を作ろうとしたか → どう指示したか → 何が起きたか・期待との違い → どう対処したか）に合わせて 4 つの小見出しで書いた。フォームが 1 つの欄なら小見出しの行ごと貼る。

**選んだ物：本番で指示役の Claude が相談なしに決定を書いて再開し、調べると製品の中の進行役が工程の輪から一度も呼ばれていなかった（11/8 09:36〜12:16、K-205〜208 → K-301）。**
選んだ理由：Claude の挙動に直接関わり、対処が具体（自動の進行役・事前の点検）で、決定ファイルと日誌に時刻つきで残っている。

### 何を作ろうとしていたか
写真を送ると係（Claude のエージェント）が自動で測り、設計図を書き、歩く画面まで人の手なしで進む流れ。11/8 は本部棟の追記（メジャー写真を足して柱間を実測にする）を、API で動かす本番として回していた。行き詰まり（事件）の時は進行役の係が決める設計だった。

### Claude にどう指示したか
事件で止まったら、指示役（Claude Code の Opus）が利用者か進行役（Fable）に相談して決定を書き、再開する、という進め方で頼んでいた。1 つ目の事件（05:25）はこの形で Fable に相談し、決定 K-201〜204 で測量からやり直した。

### 何が起きたか・期待と何が違ったか
09:35 の 2 つ目の事件（再検収 2 回で不合格の面 4）で、指示役の Opus が利用者にも Fable にも相談せず決定 K-205〜208 を書き、09:36 に再開した。利用者が止めた。調べると、進行役の係は定義と費用の枠があるのに工程の輪から一度も呼ばれず、事件を書き残して止まるだけだった。「事件は進行役が決める」は手順書の上だけで、実際は人が CLI で決定を渡していた。

### どう対処したか
K-205〜208 は案のまま取り下げ、記録を 09:35 に戻した（`scripts/rewind_honbu_k205.py`）。利用者と Fable が決め（K-301）、Opus の係が「事件が出たら道具が進行役を自動で呼び、決定ファイルで同じ記録のまま再開、3 回まで、4 回目は人」と職員の画面の承認／取り消しを実装した。押す前に審査員役（Opus）が落ちる筋 16 件を挙げ 13 件を直し、点検 `recorder agent preflight` が「Invalid API key」を捕まえた。11:33 の人の操作 1 回で、12:16 に歩く画面まで届いた。
同じ日の夕方、0 からの実走でも製図が 4 回止まり、人が決定を 1 回手で入れた。コードの失敗では進行役が呼ばれない穴が残っている。
