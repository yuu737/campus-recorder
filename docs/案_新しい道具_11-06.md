# 案：残り 2 日で効く新しい道具と改善（11/6 夜、読むだけで調べた案）

前提（コードと文書で確かめた事）：本部棟は 6 段が済／途中（`out/honbu/report.json`）、タワー75 は登録 35 枚、図書館・11 号館は「記録なし」。
撮影依頼は棟 JSON の `requests`（本部棟 33 件、`face`・`what`・`where`（文）・`why`。座標は無い）。歩く画面のタップは棟名と measured/estimated/unknown の件数と「ここ（面 id）：状態」だけで、**根拠の写真 id や値は出ない**（`web/index.html` の `pick`）。
`recorder serve` と staff の「記録を始める」は未コミット。API の係は**本物のキーで未実行**（dry-run とモックまで）。公開 URL は未決。
採点：イ＝インパクト30／デ＝デモ25／C＝Claude活用25／深＝深さ20。所要は Opus 1 本の時間。

## 3. やらない方がいい事 5 件

1. **模型に写真を貼る**：売り（記録・根拠）と矛盾し、顔・ナンバーの漏れも増える。決定済み（11-05_やること）。
2. **GPS／方位だけで写真を登録する**：本部棟 17 枚で合格 0。偽の登録が根拠を汚す。
3. **単眼の深さ・一括復元（ALIKED）を本線に入れる**：深さは散らばり 27〜54 %、ALIKED は面を裏返して 0 枚。実験の記録として残すだけ。
4. **内装の再開・新しい棟（11 号館など）の着手**：内装は写真待ちで停止中、11 号館は足元だけ。2 日で根拠の薄い棟を増やすと灰色の面が増え「決めつけない」と見た目が衝突する。
5. **大きな作り替え（glb の部品の束ね、Agent SDK の常駐、認証付きのサーバ）**：描画命令の束ねは recorder 側の設計変更、常駐は未試験のキーと費用に依る。動画の撮影を止める恐れの方が大きい。
