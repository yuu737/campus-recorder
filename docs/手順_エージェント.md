# エージェントの手順書（11/3 の手作業をそのまま手順にした物）

11/3 に本部棟・タワー75 で人（Claude）が手でやったことを、そのまま係ごとの手順に落とす。
コードの道具（`python -I -X utf8 -m recorder …`）は「定規」。判断（どの面か・何スパンか・どの部品があるか・どこを直すか）は係の Claude がする。
値は全部 `measured / estimated / unknown` と根拠付き。決めつけない。見えない物は `unknown` にして撮影依頼を返す。

## 係と分担

| 係 | 主な判断 | 使う道具 | モデル |
|---|---|---|---|
| 撮影係（速い返事） | この写真は使えるか、何が足りないか | `photos import --period during` の checks・candidates | Haiku |
| 仕分け係 | どの棟のどの面か（GPS・方位は目安。目視で確定） | 一覧画像、`data/site/tempaku.json` の足元、索引の `period`・台帳の building | Opus |
| 観察係 | 面ごとに何があるか（列数・段数・窓の形・帯・階段・設備・屋上）。比率と個数だけ | 拡大画像、観察票の書式、航空写真の切り出し（`photos roof`） | Opus |
| 数え係 | スパン数・階数の確定（複数の写真で突き合わせ） | 拡大画像、垂れ幕などの目印、`photos stitch` | Opus |
| 測量係 | 縮尺の根拠を選び、正面化→周期→m に換算。2 つ目の物差しで検算 | `photos rectify`（`--roi`）、`photos measure`、`photos stitch`、物差し台帳 `data/rulers.json` | Opus |
| 設計係 | 棟 JSON を書く（塊・面・部品・仮説）。目視の推定は方法付きで estimated | `scripts/design_<id>.py`（土台は `recorder new --from-site`）、部品の語彙（`recorder/parts_geom.py`）、CC0 アセット（`data/assets/catalog.json`）、`photos roof`、`recorder validate`、`recorder hypotheses` | Opus |
| 製図係 | 図面と模型と歩く画面を出す。判断しない | `recorder run`（validate→draw→model→overlay）。`model build` の中で自動：塊の UNION と体積検査、5 m 標高の地形、透けるガラス、手続き素材の画像への焼き込み（glb 用）、根拠の印。`site export-web --with-coverage`（HDRI・地面の質感・被覆の灰色・割合を書き出し） | コード |
| 検収係 | 写真と模型のずれ・意味の通らない部品を見て JSON を直す。直すのは design スクリプトだけ | 登録 `photos register`、再検収 `recheck`、写真の投影 `photoproj`、被覆図 `coverage`、屋上 `photos roof`、未登録の写真だけ `photos compare`／`pose`／`overlay`、検収 C の 5 項目、仮説の確定／取り下げ | Opus |

光・影・質感・地形・焼き込みは**係の判断ではなく道具の中**で毎回同じに走る（製図係の行）。係が触るのは棟 JSON（design スクリプト）だけ。

## 1 面を通す手順（本部棟 南西面で実際にやった順）

1. **取り込み**：`photos import data/photos/<日付>` → 索引。GPS 無し・ぶれは速い返事で返す
2. **仕分け**：一覧画像を見て `building` と `face` を入れる。候補は参考。方位は 180° ずれることがあるので信用しない
3. **数える**：面の両端が入る写真で、窓の列と階を数える。両端が 1 枚に入らなければ、垂れ幕・配管・角などの目印で 2 枚の列を対応させる（5＋5−1 のように）。5 階だけ小窓が 2 つ、のような例外を見落とさない
4. **正面化**：`photos rectify <写真>`。傾きの検算が 1° 以内か見る。1 枚に複数の面があれば `--roi` で壁を指す
5. **周期**：`photos measure <front.jpg>`。柱間隔÷階高の比は縮尺に依らないので、別の写真と比べて方法の検算にする（本部棟 1.306〜1.310）
6. **縮尺**：物差し台帳から選ぶ。優先順：PLATEAU の足元の辺の長さ ÷ スパン数 → PLATEAU の高さ（塔のように足元が信用できない時） → JIS のタイル 1 段（形式が確かな時だけ） → ドア・手すりなどの慣用寸法。必ず 2 つ目の物差しで検算し、差を method に書く
7. **設計**：`scripts/design_<id>.py` の形で棟 JSON を書く。塊（高さの違う部分）、面ごとの柱割り・窓・帯（引っ込みは負の depth）・水切り・ガラス張り・ピロティ、部品（笠木・箱・踊り場・室外機・配管・舗装）。見えていない面は「同じ割付と仮定」と明記
8. **検証と生成**：`recorder validate` → `recorder draw` → `model build`（鳥瞰・四面図・街路視点・glb）
9. **検収 A（正面化で）**：`photos compare <front.jpg> --building … --face …` で線ごとのずれ（m）。別の写真で検算する（1 枚から書いた JSON を残りの写真で）
10. **検収 B（写真の視点で）**：`photos pose <写真> --from-rectify <front.json> --compare <compare.json> --building … --face …` → `model build … --cameras <pose.json>` → `photos overlay <写真> --render out/<id>/view_photo_<写真>.png`。赤い線（模型）と写真の縁を見比べ、ずれている部品を列挙する
11. **直す**：ずれの一覧を見て JSON（design スクリプト）を直し、8〜10 を繰り返す。直した理由は `history` に書く
12. **足りない物**：見えなかった面・決められなかった部品は `requests` に「面・何を・どこから・なぜ」で書く。これが次の撮影依頼になる

## 登録 → 組み直し → recheck → 一覧を読む（11/4 夜から。検収 A・B の 2 回目以降はこれ）

写真ごとに「どの面の、どこを、どう写しているか」を**最初に 1 回だけ**登録し、以後は棟 JSON を直すたびに全部の写真へ自動で重ね直す。
手で `--lines`（柱の番号）を指すのは、まだ登録していない写真の 1 回目だけ。

1. **登録（1 回だけ）**：検収 A（`photos compare`。原点が曖昧なら `--lines` で柱の番号を与える）が済んだ写真を
   `recorder photos register <写真id> --building data/buildings/<id>.json --face <面> --from-rectify <front.json> --compare <compare.json> [--pose <pose.json>]`。
   既存の結果をまとめて登録するなら `recorder photos register --from-existing out/<id> --building data/buildings/<id>.json`。
   台帳は `data/photos/registry.json`（git に入る。写真は入らない）。中身は面の平面→写真の射影 `H_plane`、視点、覆う範囲、出どころ、検算の px。
   登録できない写真は理由付きで `not_registered` に入る（正面化が無い／compare が無い／原点が曖昧／面 id が棟の面でない）。
2. **組み直し**：design スクリプト → `recorder validate`。
3. **再検収**：`recorder recheck data/buildings/<id>.json --fast`（線のずれだけなら `--no-render`、写真を絞るなら `--photos <id…>`）。
   出力 `out/<id>/recheck/<日時>/summary.md`（写真 × 面 × 線：ずれ m、合否 0.15 m、前回との差）、`lines_*.png`（青＝JSON、緑／赤＝写真の縁）、`overlay_*.png`（模型の重ね）。
   線は compare と同じ集合（「面」）＋新しい部品の縁（「部品」：外階段・柱・段・玄関・室外機・窓下パネル・帯の手すり）。
   縁の強さが 2.0 未満の線は「弱い縁（参考）」で、合否と最大のずれに数えない。
4. **一覧を読む**：検収係は summary.md の NG の行だけ見る。NG は `lines_*.png` で縁の取り違え（窓の奥まりの内と外、木の縁）でないかを確かめてから JSON を直す。
5. **被覆図**：`recorder coverage data/buildings/<id>.json` → `out/<id>/coverage_<面>.svg`（色＝写真ごとの覆う範囲、灰色＝未撮影）と `coverage.json`（被覆率 %、未撮影の区間、撮影依頼の文）。
   - 写真そのものを面の座標（既定 40 px/m、`--px-per-m`）に貼り、立面の線（薄い赤）を重ねる。一番見やすいのは `coverage_<面>_check.png`（写真の合成は `_photo.png`、どれも out/ だけ。Web に出さない）。`--no-photo` で今までの塗りだけ。
   - 写真は使える所だけ：面の矩形の外・斜め（画素数／m がその写真の中央値の 1/3 未満か、視線と法線が 70° 超）・`registry.json` の各登録の `exclude`（面の m の矩形、`exclude_note` に理由）を捨て、斜線（写っているが使えない）で灰色（未撮影）と分ける。被覆率は使える範囲。重なりは画素数／m の多い写真が上。
   - 木・車などの遮蔽は自動では分からない。貼った写真を見て見つけたら `exclude` に足す。`site export-web --with-coverage` で未撮影・使えない所の矩形だけ（写真は出さない）を Web の根拠モードに灰色で重ねる。

注意：登録の後で面の位置（from / to）を同じ直線の上で動かすのは自動で直る。面の向きを変えたら、その面の写真は登録し直す。
既存の pose と最新の compare が 2 px 以上違う時は、登録の時に最新の compare から視点を解き直す（`out/<id>/registry_poses/`）。

## 写真を貼って悪い所を見つける（`recorder photoproj`。11/4 夜から。recheck の後に読む）

recheck は「決めた線」が写真の縁に合うかを見る。photoproj は線を決めずに、**登録済みの写真どうしの食い違い**から模型の形が悪い所を探す（Google Earth の投影テクスチャと同じ考え）。
写真 A を A の視点から模型に貼ると、A の視点から見る限りは必ず合って見える。別の写真 B の視点から見ると、形の違う所だけ A の模様がずれて貼られる。B の実写と比べれば、ずれた所＝形の悪い所。最終の模型には写真を入れない（改修の道具）。

1. **実行**：`recorder photoproj data/buildings/<id>.json [--photos 042900775,042822099,…] [--fast]`（写真 id は一部でよい。省略で登録の全部）。
   Blender（`blender_build.py --photoproj`）は写真の視点ごとに「画素に写る模型の点の世界座標」と「面・部品の番号」を描くだけ（通常の描画・glb は出さない）。
   投影（UV Project と同じ式）・見えるかどうか（深度の比較。裏側・厚みの無い壁の裏・70° より寝た角度は貼らない）・`exclude` のマスクは numpy。
   写真は索引のパスから直接読む（期間前は `D:\名城大学\写真資料_*`。写さない）。出力は `out/<id>/photoproj/<日時>/` だけ（写真は Web・glb に出さない）。
2. **比べる物**：縁の強さ（勾配の大きさ。色は使わない。写真ごとに 90 パーセンタイルで割って明るさの違いを消す）。写真の細かさが違えば細かい方をぼかして揃える。
   A→B と B→A の両向き。面・部品の id ごとに平均・p90。score＝その組の建物全体の平均に対する比（季節・天気の違う組でも比べられる）。
3. **読む物**：`summary.md`
   - 「悪い順（面・部品）」：score の大きい順。目安の位置（x, y, z）は一番食い違う画素の中央値。
   - 「面の中の悪い所」：面の壁を 4 m × 3 m の升（s＝面の始点から m、z＝模型の高さ m）に分けた悪い順。面全体の値では埋もれる局所の悪さ（1 階の柱・面の端）はここで見る。
   - 「1 枚しか無い所の怪しい」：他の写真が写していない所は比べられないので、写真を貼った模型を左右 ±15°・上へ 15° 回した視点で描き、模型の縁の脇に模型の縁と平行な写真の縁が増えた所に弱い印。形の決め手にはしない。
   - 「模型の縁に写真の縁が無い所」：写真 1 枚ずつ、模型の縁の脇 2 px に写真の縁がある割合が 0.3 未満の id（弱い印）。模型に在る壁・板が写真に無い（ピロティの奥の壁など）時に出る。
   - `heat_<A>_from_<B>.png`：B の実写に食い違い（青→赤）を重ね、白線＝模型の縁、上位の id に番号。
4. **判断**：上位を `heat_*.png` と写真で目視し、木・人・ガラスの映り込み・天気の違い（期間前の写真と期間中の写真の組は全体に高い）でないかを確かめる。
   形の悪さと読めたら recheck の線（m）で量を測って design スクリプトを直す。photoproj の値は寸法ではない（m に直さない）。
   笠木（coping）は空との境で縁が強いので、上に来やすい。単独で上に来ても屋根の高さを直す根拠にはしない（recheck の線で確かめる）。
5. **確かめ方**：`--keep-renders` で `render/*.npz` を残し、`--reuse-renders <dir>` で Blender を動かさずに集計だけやり直せる（棟 JSON を直した後は使わない）。
   Blender の描画と numpy の投影は画素の中心で往復 1 px 以内を毎回検査（外れたら summary の注意に出る）。

6. **本部棟 5 版で分かった読み方（11/4 夜、検収係の記録 `out/honbu/kenshu_photoproj.md`）**
   - **確かなのは 2 枚以上が重なる所だけ。** 1 枚しか写っていない部品（大階段・玄関の軒下）は上位に来ない。「1 枚の所の怪しい」も +0.03 程度で決め手にならない。撮影ガイドの「2〜3 m ずつ横に歩いて重ねて撮る」はこの道具の前提。
   - **登録した面と違う面を比べる組は信用しない**（南西面の写真と東面の写真、など）。視点が寝ていて、同じ点を三角測量すると ±4 m ぶれる。summary で面が違う組は読み飛ばす（道具の依頼：印を付ける）。
   - **score は組の平均に対する比。** 模型を直して全体が良くなると、直していない物の score が上がる。前後の比較は平均の絶対値（組の平均、升の平均）で見る。
   - **笠木・パラペットは空との境で必ず上に来る。** 形の根拠にしない。recheck のパラペットの線が合格なら無視。
   - **「模型の縁に写真の縁が無い所」が一番効いた。** ピロティの奥に生成器が残した厚さ 4 cm の偽の壁と、北東面の線の膜（通り抜けが塞がる）はこれで見つかった。模型に在る物が写真に無い時は、まず生成器の癖（開口の境・奥行きが向かいの面と同じ時）を疑う。ID 画像で id を特定する。
   - **奥行きは 2 枚で三角測量**：同じ点（扉の角・ガラスの枠の角）を 2 枚で 5 点指し、登録の視点から交点を出す。本部棟 東面 1 階のガラスは 2.14〜2.54 m（5 点）→ 2.3 m。1 点だけで決めない。
   - **遮蔽は exclude に足してから読み直す**：植え込み・垂れ幕・木が上位に来る。足したら `--reuse-renders` で集計だけやり直せる。
   - 升の上位（4 m × 3 m）は面の端と 1 階に集まりやすい。面の端は「長さの食い違い」（東面 28.2 m vs PLATEAU 30.8 m）、1 階は「奥行き・柱・遮蔽」のどれかをまず疑う。

## 利用者が決めた模型の方針（11/4。係はこれに従う）
- **本部棟を先に「納得できる水準」まで**：観察票にある 1 m より大きい部品が全部模型にあり、検収で位置 0.3 m 以内。素材・光はその後。他の棟は同じ道具で追いつかせる
- **意味の検査（検収 C）**：線が合っていても「役割を書けない部品」「役割に合わない大きさ」「航空写真に無い屋上の物」「二重計上」は不合格（屋上の塔屋 8 m の箱が例）
- **航空写真は倒れ込みを測ってから使う**（`photos roof`）。屋上の縁のずれ（緑−赤）が補正量
- **語彙は足す**。無い物を箱で近似しない。定型の物は CC0 アセット、ガラスは透ける
- **穴埋めパズル**：全体を 1 枚に収めなくてよい。部分写真を登録して被覆図で足りない所を灰色に。未撮影の面は灰色の壁（タイル色の「窓の無い壁」にしない）
- **写真は改修の道具**：模型に貼って食い違いから悪い所を見つける（`photoproj`）。最終の模型に写真は入れない
- **未確定は仮説として置き、戻せるようにする**（`basis: "hypothesis"`、根拠は対称・同じ塊・足元の 3 つだけ。縞で見せる）
- **歩く画面と Blender の見た目を揃える**（焼いたタイル・HDRI・影・地形）。地面は面ごとの板ではなく 5 m 標高の地形

## 検収係の判断の目安

- 階高・柱間隔の比が別の写真で 1% 以内に合えば、方法は通っている。合わなければ正面化の面の取り違えを疑う
- 線のずれが 0.15 m 以内なら合格。0.15〜0.5 m は JSON の値を直す。0.5 m 以上は対応の取り違え（窓の下端と水切りなど）を先に疑う
- 斜めの写真を正面化すると、窓の奥行きぶんの見込み面が帯になって写り、縦の線が ±0.5 m ぶれる。横の線（高さ）を主に信用する
- 重ね合わせで模型の線が写真の縁の外側に出ていれば、その部品は大きすぎる（または位置が手前）。内側なら小さすぎる

## 11/3 深夜に分かったこと（タワー75 で手作業したことの手順化）

### 観察票 → 設計（観察係と設計係の受け渡し）
- 観察係（Opus）は面ごとに「列数・段数・窓の形・柱型と窓の比・帯・ガラス・角・足元・頂部・仮の設計との食い違い・不明」を決まった書式で書く（`out/tower75_観察票.md/.json` が見本）。寸法は書かない。比率と個数だけ
- 設計係はそれを部品に落とす。列数 → `bays.count`、比 1.35:1 → `pier_width`、「無地」→ 窓なし、「各階に小窓 1 つ」→ `count=1` の面、「凹部の全面ガラス」→ `glazing`＋各階の `ledges`（ルーバー）、「頂部のガラスの箱」→ `box` 部品（material glass）
- 観察票の「仮の設計との食い違い」は必ず読む。タワー75 では写真 11 が南南西面ではなく西北西面だったことがここで分かった（1 版の面の取り違え）
- 観察票の `face_reassignment` で索引の `face` も直す（設計スクリプトが読んで `data/photos/index.json` を更新する）

### 面の id と形
- 面の id は足元の辺の番号で固定し（`f0`〜）、観察票・索引・設計で同じ id を使う。設計で面を作り直すときも id を変えない
- 一直線に並ぶ辺（法線の差 3° 以内）は 1 つの面にまとめてから柱割りを通す（タワー75 の西北西面 f1+f2+f3 → `W`）。まとめた面は元の id を `merged` に残す
- 足元の凹部の深さなど OSM と写真が食い違う所は、写真に合わせて頂点を動かし、`footprint.method` にそう書く

### 高さの物差しの検算
- PLATEAU の高さは「部品がどこにあるか」を航空写真で確かめてから使う。タワー75 では 74.2 m の部品が足元の外にあった
- それでも値を使うなら、独立した長さで検算する：西北西面 32.6 m（OSM）に 9 列 × 3.43 m（写真の周期を 74.2 m で換算）が収まるか。収まれば整合、90 m なら 37 m で収まらない
- 航空写真の倒れ込みは「測る」。周りの低い棟の倒れ込み率（0.13〜0.17）と比べて高さの検算にも使える

### 航空写真の屋上の精読（`recorder photos roof`）
- 航空写真は高い物ほど写真の中心から外へ倒れて写る（倒れ込み）。足元（PLATEAU/OSM）をそのまま重ねると屋上の縁とずれるので、**屋上の物は「写真の上の位置 − 倒れ込み」で足元の座標に戻す**
- 実行：`recorder photos roof data/buildings/<id>.json [--out-dir out/<id>] [--roof-edge "x,y;x,y;..."] [--units "x,y,w,d;..."]` → `out/<id>/roof.json` と `roof_aerial.png`（6 倍、枠に m の目盛り。赤＝足元、緑＝推定した屋上の縁、黄＝設備と番号、水色＝既存の屋上部品を上端の高さの分だけずらした位置）
- 縁：足元の形を ±6 m 平行移動して、写真の明るさの勾配（辺に直交する成分）といちばん重なる位置。塊（`blocks`）があれば塊ごとに高さに比例してずらす（低い塊は倒れ込みが小さい）。候補の上位 3 と確からしさを出し、1 位と 2 位の点の比が 0.92 以上なら `ambiguous: true`
  - 長い棟は「長い辺に沿った向き」の候補が並びやすい（本部棟で 1.1 m 違いの 2 位）。**ambiguous のときは拡大画像で屋上の角を 2〜3 点（違う向きの辺の上）読み、`--roof-edge` で渡す**。人の点が自動より優先
- 倒れ込み率 `lean_ratio = |lean| / 屋上の高さ（地面から）`。0.05〜0.25 の外は警告（写真の位置ずれか縁の読み違い）
- 検算：近くの低い建物（PLATEAU の参考高さ 5 m 未満）で同じ走査。ずれが 1 m 未満なら写真の位置合わせは良い。1 m 以上なら、そのずれは**写真と足元データの位置合わせのずれ**の可能性があり、本体の lean から引いて考える（引いた値を JSON には書かず、method に両方書く）
- 設備：屋上の縁から 1 m 内側で、塊ごとの屋根面の明るさの中央値から閾値（22 か 3.5×MAD）以上違う連結成分。大きさは 2 次モーメント（棟の長い辺の向き）で、1 m 未満は捨てる。30 m² を超える物は `large_regions`（多くは高い塊の影）。暗い塊は影を含むので、箱の大きさは影の分だけ大きく出る
  - 塊より高い部品（階段塔など）の上に載っている物は `on_part` と、その高さの倒れ込みで戻した `cx_if_on_part` も出す
  - `--units` で人が指した物（写真の上の中心 m と w,d）が優先。自動の結果は `units_auto` に残る
- 設計係は `roof.json` を読んで `rooftop_units` を書く：status は `estimated`、evidence に `gsi:aerial_z18`、method に「recorder photos roof、lean_m、自動か人の指定か」。`existing_rooftop_parts` が「写真では中に設備が無い」なら、その部品は根拠を失っているので見直す
- 本部棟（2026-11-04）：lean (−0.50, −4.75) m・率 0.20（ambiguous、2 位 (+0.50, −5.25)）、低い建物 osm-way-1304077542 は (+1.0, −1.0) m ずれ（1 m 以上）。模型の塔屋の位置には何も写っていない

### 視点の逆算（検収 B）
- **手で写真の角を指す方法は失敗した**（8 点で再投影誤差 数百 px）。Claude が拡大画像から画素を読むのは不正確
- 成功した方法：正面化の射影変換 H と、検収 A で合わせた原点（`x_origin_px`・`z_origin_px`・`px_per_m`）をつなぐ → 面の平面（m）→ 写真（px）の射影変換 → 面の格子点で PnP（IPPE）。再投影 0 px、カメラ高さ 1 m 前後なら合っている
- つまり検収 B は検収 A の後にしかできない（正面化できた面だけ）。斜めの写真しか無い面はまず正面化（ROI 指定）から

### 生成器の教訓
- 窓の彫り込みは**面ごと**に結合してブーリアン。全部を 1 つに結合すると、角で隣の面の窓と食い込んで自己交差になり、EXACT が黙って失敗する（タワー75 で窓が消えた）
- 接する箱（ピロティとガラス張り）は別々に当てる
- **塊（高さの違う部分）が平面で重なる棟は、`join` ではなく足し算のブーリアン（EXACT UNION）で 1 つにする。** join だと同じ空間が二重に入った自己交差になり、最初の窓の彫り込みで塔の本体が丸ごと消える（タワー75 で窓が「小さな印」にしか見えなかった原因。11/4 未明に切り分け、`union_bodies()` と彫るたびの体積検査 `check_cut()` を入れた。記録は `out/tower75/窓の切り分け.md`）
- **地面は面ごとの板にしない。** 面の幅×奥行き 12 m の仮の板は重なり・入隅で建物に食い込み、屋根伏せが白い多角形で埋まった（11/4）。地面は 5m 標高から ground_z を引いた地形 1 枚（`site.terrain_grid`、足元の外側 20 m、1 m 格子、5 m 窓で画素の段を均す）。建物は地形を切り欠かず `footing_*` で地形の 1 m 下まで伸ばす。屋根伏せ・四面図では地形を描かない
- `faces[].ground_offset` は形に使わず地形との検算だけ（面の前 0〜12 m の中央値と比べ、tol 超えは model_report の warnings）。室外機・段・玄関・外階段の足元は面の前の地形（面から 0.5〜3 m の中央値）から取る
- カーテンの色はタイルと紛れない暗めに。細い窓の帯はカーテンで埋まって壁に見える
- 塊の「上だけ引っ込む角」は `bottom_z` で試作したが、位置が決まらず絵が崩れた。寸法が unknown の物は塊にしない（撮影依頼に回す）
- **部品の語彙（11/4 追加）**。形は `recorder/parts_geom.py` の 1 か所で作り、模型と立面図が同じ形を使う。値は全部 `{"value","status","evidence","method"}`（裸の数は検証で落ちる。座標の x, y, polygon, center だけ裸でよい）。`along` は面の始点から部品の from 側の端まで。見本は `tests/fixtures/parts_building.json`
  - `stair_switchback`（折り返しの外階段）：`{face, along, width, depth, floors+floor_pitch か landing_z[], landing_len, parapet{height}, rail{height,post_pitch}, pilotis{count,size}, exit_box{height}, canopy{shape:"barrel",rise}}`。斜めの段は傾いた板、外側と内側の通路を交互に使う
  - `porch`（玄関の軒下）：`{face, along, width, depth, height, glass{along0,along1,depth,mullion_pitch,transom_pitch}, columns{width}}`。壁をブーリアンでくり抜く（`check_cut` で体積検査）
  - `steps`（段の塊）：`{face, along, width, depth, count, rise, tread, sides:["from","to"], edge:"straight"|"curved", radius}`。sides で L 字に回る、curved は同心の円弧
  - `faces[].windows[].spandrel`（窓の下の濃いパネル）：`{height, depth, material}`
  - `rail`（手すり）：部品 `{face, along0, along1, z, height, post_pitch}` か、帯に `bands[].rail{height, post_pitch}`
  - `column`（単独の柱）：`{x, y, diameter, z0, z1, section:"round"|"square"}`（世界座標）
  - `rooftop_units`（屋上の設備）：`{source:"aerial", lean_correction_m:{value:[dx,dy],...}, z0, units:[{center,w,d,h} | {polygon,h}]}`。位置は航空写真で読んだまま書き、生成器が補正を足す
  - `ac_units.z0`：壁付けの室外機の下端。省略すると面の前の地面（ground_offset）＋0.1 に置く（地面の板に埋まらない）
- **部品の語彙 その 2（11/4 午後、本部棟で見送られた 9 種）**。値は全部測定値の形。テストは `tests/test_parts_vocab2.py`
  - `ceiling_beams`（天井の小梁）：`{face, along0, along1, depth, z（天井の高さ）, pitch, beam_width, beam_height, side:"in"|"out", direction:"across"|"along"|"grid", pitch_n}`。梁は z から下へ成の分
  - `louver`（ルーバー）：`{face, along, width, z0, z1, blade_pitch, blade_width, blade_thickness, angle（度）, orientation:"horizontal"|"vertical", offset}`。羽根は区画の中心に置く
  - `planter`（植え込み）：`{face, along, width, depth, offset}` か `{x, y, width, depth, yaw}` か `{polygon}`＋`{height, wall, material}`。縁の中は緑（縁より 5 cm 低い）。単独で z0 が無ければ地形から
  - `nameplate`（銘板・看板）：`{face, along, offset}` か `{x, y, yaw}`＋`{width, height, thickness, z0, material:"stone"|"metal"|"dark"}`
  - `patch`（面の一部の素材）：`{face, along0, along1, z0, z1, material}`。壁から 5 mm 浮かせた 5 mm の板。material は名前か `asset:<id>`
  - `vestibule`（風除室）：`{polygon, wall_edges:[壁に付く辺の番号], z0, height, mullion_pitch, transom_pitch, roof{thickness, overhang}}`
  - `pergola`（パーゴラ）：`{polygon, z0, height, post_pitch, post_size, beam_pitch, beam_width, beam_height}`。小梁は最初の辺に平行
  - `bridge`（渡り廊下）：`{from:[x,y], to:[x,y], z_from, z_to, width, height, walls:"full"|"glass"|"parapet"|"none", roof}`。床は両端の高さを結ぶ斜めの板
  - `curved_glass`（曲面ガラス）：`{face, along0, along1, radius, z0, z1, mullion_pitch, transom_pitch, cap}`。弦から外へふくらむ 24 分割の円弧、奥の壁に室内の暗い板。半径が弦の半分より小さいと検証で落ちる
  - `stair_switchback.landing_len_from / landing_len_to`：両端で長さの違う踊り場。`end_parapet:["from","to"]` から外した側は端の腰壁を立てない（隣の床へ続く所に実物に無い壁が出ていた）
  - `spandrel.in_recess: true`：窓下のパネルを窓の奥まりの中（ガラスと同じ奥）に置き、窓の彫り込みをパネルの下端まで下げる
  - 単独の部品（風除室・パーゴラ・渡り廊下・x,y の植え込み）は立面図では面より手前に出ている物だけを頂点の凸包で描く。立面の部品は部品をまたいで奥から順に描く
- **透けるガラス（11/4 午後）**：Blender は Principled の Alpha 0.35（淡い青緑、IOR 1.5、粗さ 0.05、BLENDED）、glb は alphaMode BLEND、歩く画面は名前に glass を含む素材を transparent・depthWrite なしにする。ガラスの奥が壁（タイル）だと透けて変になるので、窓はガラスと彫り込みの奥の面の間にカーテン（暗め 0.20）、glazing は彫り込みを 0.1 m 深くしてガラスの薄い板＋奥に室内の暗い箱（interior）、porch のガラスの箱は奥の壁から 5 cm 離して暗い板。カーテンを彫り込みより奥に置くと壁の中に埋もれて見えない（それまでの 0.6 m 奥は埋もれていた）

## アセットの使い方（CC0。見た目だけ借りる）

- **分担**：位置・個数・大きさは棟 JSON の根拠付きの値、見た目（形の細部・質感の写真）は CC0 の公開アセット。アセットの寸法を棟 JSON に書き写さない
- **台帳**：`data/assets/catalog.json`。項目は `id / kind(model|texture|hdri) / what / source / url / license / license_url / fetched_at / file / size_m / note / sha256`。**CC0-1.0 以外（CC-BY も）は入れない**（`recorder.assets.validate_catalog` が落とす）。探して無かった物は `not_found[]` に「該当なし → 箱のまま」と書く
- **取得**：`python -I -X utf8 -m recorder assets fetch [id ...]`（`scripts/fetch_assets.py` も同じ）。Poly Haven は公開 API（`/files/<id>`）から 1k を取り、md5 を確かめ、SHA256 を台帳に書く。2 回目からは差分だけ。model は取得後に gltf の外形を測り、`size_m` を測った値にする（1 つの gltf に色違いが並ぶ物は `node` で 1 つ選ぶ）。Kenney は署名つきの一時リンクなので自動では取らず、手で落とした zip を `assets/kenney/` に置く。取得物は `assets/`（git 管理外）の中だけ。そこから何も実行しない
- **一覧**：`recorder assets list [--kind model]`（取得済みか、実寸、該当なし）
- **棟 JSON に書く**（設計係）：
  - 置く物：`{"type": "asset", "asset": "ac_outdoor", "face": "S", "along": 測定値, "offset": 測定値, "z0": 測定値, "yaw": 0, "count": 測定値, "pitch": 測定値, "size": {"w": 測定値, "d": 測定値, "h": 測定値}}`。面に付かない物（木・街灯）は face/along の代わりに `x, y`
  - `size` の w/d/h は鍵を必ず書く（見えなければ unknown）。裸の数・根拠の無い measured は検証で落ちる。`yaw` は置き方の角度（度）なので裸の数でよい（0＝模型の正面が面の外を向く）
  - 質感：既存の部品の `"material": "asset:brick_ochre"` のように台帳の texture を指せる（台帳に無い id・model を指すと検証で落ちる）
- **模型**（`recorder/assets_blender.py`、Blender の中だけ）：`build_asset_parts(b, col)` が parts[type=asset] を全部置く。中身は `import_model(id, at, yaw, size_m)`（底面の中心を原点に揃え、台帳の size_m と部品の w×d×h の比で軸ごとに拡大。unknown の軸は他の軸の比で揃えて「仮」と警告。拡大率が 0.5〜2 の外なら警告＝アセットの選び方が違う疑い）、`material_from_texture(id)`（基本色・法線・粗さを箱投影、tile_m で実寸）、`set_world_hdri(id)`
- **along が unknown の物は置かない**（決めつけない）。警告は標準出力と返り値に出る

## API で動かす（`recorder/agents.py`）

- 同じ `.claude/agents/*.md` を Claude Agent SDK で実行する。`recorder agent list` / `agent run <係> --task "…" [--dry-run]` / `agent pipeline <棟id> [--steps shiwake,kansatsu,…] [--dry-run]`
- 工程の順は 撮影→仕分け→観察→数え→測量→設計→製図（コード、`recorder run --fast`）→検収→製図（コード、本番の `recorder run`）→歩く画面（コード、`site export-web --with-coverage`）。各段は `out/<棟id>/pipeline_<日時>.json` に係名・model・秒・出力・トークン・費用を残す
- キーは環境変数 `ANTHROPIC_API_KEY` のみ。リポジトリ・JSON・日誌に書かない。無ければ本実行は止まり、`--dry-run` だけ使える
- 費用の上限は 1 回の呼び出しごと（haiku 12 ターン/$0.5、sonnet 20/$1.5、opus 30/$4）。超えたら止めて記録し、pipeline はそこで中断する
- model は haiku/sonnet/opus を `claude-*-5-5` に対応。定義に fable とあれば opus に落として警告（Fable は人の役）
- **まだ本物のキーでは試していない**（dry-run と SDK をモックした試験まで）

### 試走のやり方（本番と同じ出発点から、写真だけで歩く画面まで。11/4）
1. **退避**：`python -I -X utf8 scripts/trial_reset.py <棟id>` → 設計スクリプト・棟 JSON・`out/<id>/`・`out/<id>_*`・その棟の正面化・仕分け・glb・登録（registry のその棟の分）・索引の face を `trial/<id>/<日時>/` へ（一覧は `manifest.json`）。building は台帳由来なので残す（`--clear-building` で台帳由来でない物だけ空に）
2. **依頼文**：`recorder agent tasks <棟id> [--photos <folder>]` → `out/<id>/agent_tasks.json`・`.md`。依頼文は (工程, 棟, 写真フォルダ) だけで決まり、`agent pipeline` と 1 文字も違わない
3. **工程ごとに係**：指揮役が `subagent_type=<agent>` で task を**そのまま**渡す（system は係の定義。API では `_共通.md`＋定義）。コードの工程（seizu・seizu_final・web）は `command` を指揮役が打つ
4. **記録**：工程ごとに `recorder agent log <棟id> --step <工程> --model opus --seconds N --tokens N --note "…"` → `out/<id>/pipeline_<日時>.json`（runner subagent。API の記録と同じ形）
5. 係が止まったら直さずに止まった所と理由を note に書く（手で埋めると試走にならない）
6. **戻す**：`python -I -X utf8 scripts/trial_reset.py <棟id> --restore` → 退避を元に戻し、試走の結果は `trial/<id>/<日時>/after/` に残る（索引・台帳は `index_after.json`・`registry_after.json`）
7. 戻す前に 2 回目の退避はできない（元を上書きしないため）。`trial/` は git 管理外
8. 注意：git の履歴と `docs/`（この手順書の「本部棟で実際に出た数」など）には前の結果が残る。係には読ませない運用で補う

## 歩く画面と Blender の見た目を揃える（11/4）
- 手続き的な素材（タイル）は glb に出ないので、`model build` が書き出しの直前に周期（目地の整数倍、約 3 m）の板へ基本色を焼き、`out/<id>/tex/<素材>_color.png` を glb に入れる（`--fast` 512 px、通常 1024 px）。法線は描画用の素材に凹凸がある時だけ。時間は model_report の `web_bake`
- 模様・画像の素材は m 単位の UV（名前 `UV`。壁は面に沿った水平距離と高さ）で貼る。描画も glb も同じ UV。タイルはこれまで物体座標の x, y で貼っていて壁では縦縞だった（直した）
- CC0 の画像素材（`asset:<id>`）は焼かずにそのまま glb に入る（UV `UV` ÷ tile_m、KHR_texture_transform）
- 比較：`model_report.json` の `web_cameras.street.query` を `web/index.html?<query>&size=1400x1000&ui=0` に付けると、`persp_street.png` と同じ位置・向き・縦の画角で描く
- 生成物（tex・glb）は手で直さない。見た目を変える時は blender_build の素材か棟 JSON の materials を直して作り直す

## 根拠の層（11/4。歩く画面の「根拠で見る」）
- 面・部品の状態は `schema.evidence_summary(b)`：形を決める値（bays.count/pitch/pier_width、窓・帯・開口・ガラス・水切り、floor_pitch、面の上端）を集め、全部 measured→measured、`"basis": "hypothesis"` の値あり→hypothesis、芯（柱の数か窓などの開口）が分からない→unknown、それ以外（混在・細部に unknown）→estimated
- 割合は 2 つ：形がある割合＝unknown でない面・部品 ÷ 全数、根拠がある割合＝measured の値 ÷ 全測定値（photos・requests・history は除く）
- `model build` が glb の node と素材の extras に `evidence`・`face`・`part` を付ける（本体の壁は面ごとに素材を分けて印）。unknown の面の壁は描画も glb も灰色（`unknown_face`）
- `site export-web` が site.json の designed に `shape_ratio`・`evidence_ratio`・`faces`・`parts`・`body` を入れる。仮説の値を置く時は値に `"basis": "hypothesis"` を足す（status は estimated のまま）
- 面の振り分けは面の線から奥 3 m・外 0.3 m の縦の面だけ。ピロティの奥の壁などは本体（塊）の印になる
